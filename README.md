# Android Security Lab · Android 14

Практическая лаборатория для курсовой «Исследование встроенных механизмов безопасности мобильной ОС Android». Шесть опытов выполняют реальные операции Android. **Наличие исходников и успешная сборка не означают успешное выполнение опытов.** Фактический статус появляется только в отчёте конкретного запуска.

## Запуск без Android Studio

1. Распакуйте ZIP. Создайте новый пустой репозиторий GitHub.
2. Загрузите **содержимое** папки `android-security-lab` в корень репозитория. В корне должны находиться `README.md`, `settings.gradle.kts`, `gradlew`, папки `lab`, `helper`, `sample`, `common`, `scripts`, `tests`, `gradle` и **`.github`**. Не загружайте только ZIP и не вкладывайте весь проект в дополнительную папку.
3. Убедитесь, что GitHub показывает файл `.github/workflows/security-lab.yml`. Папка `.github` может быть скрыта в файловом менеджере. Если веб-загрузка её пропустила, используйте GitHub Desktop: скопируйте всё содержимое распакованной папки в локальную папку нового репозитория, выполните Commit и Push. Создавать или редактировать файлы не нужно.
4. Откройте **Actions → Android Security Lab — полное исследование → Run workflow → Run workflow**. При необходимости предварительно разрешите Actions для репозитория.
5. Дождитесь задания «Отчёт по всем шести опытам». Скачайте артефакт **`securitylab-report`**, распакуйте и откройте **`report.html`** обычным браузером. Изображения встроены в HTML; для переходов к исходным журналам сохраните рядом папку `evidence`.

Не нужны GitHub Secrets, PAT, доступ к телефону или ручное взаимодействие с эмулятором. Приватный репозиторий расходует доступную квоту GitHub Actions. Время первого запуска зависит от скачивания SDK и образа AVD; workflow ограничен 55 минутами на группу.

**Если workflow красный:** это не обязательно ошибка сборки. Все шесть опытов должны быть PASS, чтобы итоговая проверка стала зелёной. Скачайте отчёт и `raw-standard` / `raw-credentials`; они сохраняются и при ошибках, если GitHub runner смог выполнить шаг загрузки. Передайте диагностический архив для исправления, не меняя код наугад. При жёстком отключении/отмене runner сохранение последних материалов не гарантируется.

## Что получится после запуска

| Артефакт | Содержимое |
|---|---|
| `securitylab-report` | Русский `report.html`, `results.json`, `junit.xml`, краткий `summary.md`, папка исходных доказательств |
| `raw-standard` | APK, журнал сборки, подписи APK, результаты подписи/tapjacking/TLS/MediaProjection, PNG и системные журналы |
| `raw-credentials` | APK, журнал сборки, результаты Direct Boot/Keystore, PNG и системные журналы |

В каждой группе создаётся собственный чистый AVD и собственные одноразовые сертификаты. **Не смешивайте APK разных групп или запусков:** их подписи и лабораторные CA различаются. Артефакты хранятся 14 дней — скачайте нужный запуск заранее.

## Среда и архитектура

- Android 14, API/targetSdk/minSdk 34; Google APIs x86_64, профиль Pixel 2, 720×1280, density 240.
- Java 17, Gradle Wrapper 8.13, AGP 8.13.2, Kotlin 2.3.20. Kotlin-исходники полностью находятся в репозитории.
- `lab` → **Security Lab**: записи DE/CE, AES/GCM, целевая кнопка, сетевые запросы, защищаемое окно.
- `helper` → **Lab Helper**: окно другого UID и foreground service реального MediaProjection.
- `sample` → **Update Sample**: версии 1/2 одного приложения с постоянной записью. Из одного исходника собираются три APK с разными параметрами версии/подписи.
- `common`: простой интерфейс и протокол журналирования фактических результатов.
- `scripts/run.py`: ADB, поиск системных элементов через UI Automator, контроли, сбор доказательств.
- `scripts/report.py`: отчёт, проверка происхождения/хешей изображений, JSON/JUnit.

На главном экране выбирается предметный опыт. Статусы PASS/FAIL предназначены для отчёта. Приложение показывает запись, версию, результат настоящего запроса или исключение API. Системными являются PIN, согласие захвата и экран блокировки; сообщения приложения явно остаются сообщениями приложения.

## Правила методики

Каждый опыт содержит положительные и отрицательные контроли. Отказ операции засчитывается только с соответствующей причиной и действующим положительным контролем. Ошибка подготовки не считается защитой.

| Статус | Значение |
|---|---|
| PASS | Выполнены все критерии конкретного опыта, сохранены обязательные доказательства |
| FAIL | Наблюдение противоречит проверяемому критерию; требуется разбор журналов |
| ERROR | Сбой выполнения, среды, поиска системного UI или целостности доказательств |
| INCONCLUSIVE | Наблюдений недостаточно для заявленного вывода либо необходимая возможность AVD отсутствует |
| NOT_RUN | Результат опыта не поступил, например сборка/запуск эмулятора завершились раньше |

JUnit: FAIL → failure; ERROR → error; INCONCLUSIVE/NOT_RUN → skipped. Итоговый workflow требует шесть PASS, поэтому skipped не создаёт ложного общего успеха.

Для каждой команды приложения создаётся уникальный token; журнал содержит UID, package, время и реальный результат. Для запуска записываются commit, GitHub run/attempt, fingerprint, API, сведения о SDK и хеши APK. Скриншоты создаются заново; отчёт проверяет их SHA-256 и run_id. Никаких заранее подготовленных изображений в проекте нет. Подробный протокол: [docs/methodology.md](docs/methodology.md).

## 01. File-Based Encryption / Direct Boot

**Цель.** Проверить доступность существующих DE/CE-записей до первого PIN после настоящей перезагрузки.

**Действия.** Автоматизация задаёт одноразовый PIN, приложение создаёт две случайные записи и хеши. После `adb reboot` directBootAware receiver обрабатывает `LOCKED_BOOT_COMPLETED` и реально читает обе записи. Затем автоматизация вводит PIN через системный интерфейс и повторяет чтение. Обычная блокировка после первого PIN проверяется отдельно по состоянию пользователя.

**Критерий.** До разблокировки `isUserUnlocked=false`, DE читается, CE возвращает исключение; после неё читаются исходные байты обоих файлов. Номер загрузки увеличился. Повторная блокировка оставляет пользователя `RUNNING_UNLOCKED`.

**Доказательства сразу после опыта в отчёте:** подготовленные записи; настоящий экран первичной блокировки; результаты чтения после PIN; `boot_receiver`, хеши, исключение CE и `dumpsys user`. Скриншот блокировки не является самостоятельным доказательством FBE.

**Ограничение.** Требуется `ro.crypto.type=file`. Искусственное `sm set-emulate-fbe` не используется. Опыт исследует доступность CE/DE, не криптостойкость шифрования диска и не защиту физического ключевого хранилища.

**Вручную.** На чистом AVD установите PIN в Settings → Security, откройте опыт, подготовьте записи, перезагрузите AVD. Не вводите PIN до сохранения Logcat. После PIN вернитесь в опыт и нажмите проверку доступа. Строки `ASL_CHUNK` — фрагменты Base64 JSON, полный журнал также хранится в DE-файле приложения.

## 02. Android Keystore с PIN

**Действия.** Создать AES-256 GCM ключ AndroidKeyStore с `setUserAuthenticationRequired(true)`, `AUTH_DEVICE_CREDENTIAL` и окном 30 секунд. Подтвердить PIN в настоящем окне Android. Зашифровать случайную запись, расшифровать и проверить хеш. Через 35 секунд повторить операцию без новой аутентификации, затем снова подтвердить PIN и открыть тот же шифротекст.

**Критерий.** Положительные расшифрования совпадают; отрицательная операция получает `UserNotAuthenticatedException`, а не произвольную ошибку. Сам ключ не экспортируется; свойства KeyInfo записываются отдельно.

**Доказательства в отчёте:** системный запрос PIN, открытая запись, исключение после тайм-аута, повторное открытие; шифротекст, совпадение байтов и KeyInfo. Системное окно PIN может отсутствовать на ADB-скриншоте, если сама ОС защищает его захват: в таком случае главным свидетельством остаются системный UI и операция Keystore, а не нарисованная замена окна.

**Ограничение.** Это доступ в течение 30 секунд, а не PIN перед каждым вызовом `doFinal`. Эмулятор не доказывает физическую TEE/StrongBox. Все данные синтетические; расшифрованная тестовая запись намеренно видна в отчёте.

**Вручную.** Установите PIN, создайте ключ в приложении, подтвердите PIN, подождите более 30 секунд и нажмите «Попытаться расшифровать без запроса», затем снова подтвердите PIN. PIN приложение не получает.

## 03. Проверка подписи при обновлении

**Действия.** Установить `sample-v1-a.apk`, открыть приложение. Выполнить `adb install -r sample-v2-b.apk`, затем проверить неизменность версии/данных. Выполнить `adb install -r sample-v2-a.apk` и проверить переход на v2 с той же записью.

**Критерий.** B отклонён с `INSTALL_FAILED_UPDATE_INCOMPATIBLE`; A принят. Версия и SHA-256 записи проверяются после каждого шага. `apksigner verify --print-certs` подтверждает реальные подписи.

**Доказательства в отчёте:** исходная версия, состояние после отказа, версия 2 с сохранённой записью; файл `incompatible-update.txt` с ответом Package Manager и сертификаты APK. **При ADB-установке системного окна отказа нет.** Не рисуем его в приложении.

**Ограничение.** Независимые сертификаты без signing lineage. Корректная подпись не означает безопасность самого приложения.

**Вручную.** Используйте три APK только одной группы/одного запуска и указанные команды. Перед повторением удалите Update Sample; это удалит его лабораторную запись.

## 04. Защита от Tapjacking

**Действия.** Нажать целевую кнопку без наложения. Helper создаёт полноэкранное `TYPE_APPLICATION_OVERLAY` другого UID с `FLAG_NOT_TOUCHABLE`, `alpha=0.9`. Повторить касание в тех же координатах. Затем Security Lab вызывает `setHideOverlayWindows(true)`, после чего кнопка снова нажимается. Снятие скрытия должно вернуть всё ещё существующее окно Helper.

**Критерий.** Под overlay событие не доставляется в Activity; InputDispatcher указывает недоверенную окклюзию Helper. При скрытом overlay целевая запись изменяется. Отсутствие клика без записи причины — INCONCLUSIVE.

**Доказательства в отчёте:** обычная кнопка, настоящее голубое окно Helper, экран после системного скрытия и повторное появление overlay; счётчики входных событий и журнал InputDispatcher.

**Ограничение.** Не исследуются все виды tapjacking. Системная блокировка касаний не отключается. Разрешение overlay заранее выдано через appops только как подготовка.

**Вручную.** В Lab Helper разрешите наложения, в Security Lab откройте кнопку, затем в Helper включите окно. Чтобы скрыть непрозрачное окно, используйте команду `adb shell am start -n ru.securitylab.lab/.MainActivity --es op hide_overlay --ez enabled true`; попытка нажать кнопку под заблокированным окном намеренно не работает. Удалить окно можно командой для Helper с `--es op overlay_stop`.

## 05. TLS и Network Security Configuration

**Действия.** На runner запускаются три локальных TLS-сервера и один HTTP. 8443: доверенный CA и корректный IP SAN. 8444: независимый CA. 8445: доверенный CA, но чужое имя. Запросы идут через стандартный `HttpsURLConnection`, без самописного разрешающего TrustManager. HTTP на `10.0.2.2` запрещён; тот же сервер доступен контрольным запросом через `localhost` и `adb reverse`, для которого NSC явно разрешает HTTP.

**Критерий.** Положительные ответы содержат nonce текущего сервера. Отказы раздельно подтверждены исключениями проверки цепочки, имени и cleartext policy.

**Доказательства в отчёте:** полученный ответ и фактические исключения четырёх вариантов; успешный контроль HTTP; журналы сервера и сертификат TLS-сеанса.

**Ограничение.** Проверяется штатный HTTP/TLS-стек приложения. NSC не блокирует произвольные нативные сокеты на уровне всей ОС. Лабораторный CA добавлен только в APK и только для лабораторного домена. Частные ключи и серверные сертификаты создаются заново при сборке; срок действия 7 суток.

**Вручную.** Потребуется локальная сборка из той же `.lab-secrets`, затем `python scripts/server.py`, `adb reverse tcp:8080 tcp:8080`. Выберите варианты соединения в приложении. APK из GitHub не предназначен для проверки с заново сгенерированным другим CA — используйте CI либо пересоберите локально.

## 06. MediaProjection и FLAG_SECURE

**Действия.** Helper показывает системное согласие на захват дисплея; foreground service получает MediaProjection, регистрирует callback и создаёт VirtualDisplay с ImageReader. Security Lab показывает тестовую запись и яркий маркер. Сохраняются реальные кадры: обычное окно → FLAG_SECURE → обычное окно. На том же MediaProjection вызывается второй `createVirtualDisplay`.

**Критерий.** Маркер присутствует в первом и третьем кадре и отсутствует во втором. Новый кадр поступает через ImageReader; файл проверяется по хешу. Повторный вызов возвращает `SecurityException`. Первый VirtualDisplay должен быть успешно создан — иначе опыт не засчитывается.

**Доказательства в отчёте:** настоящий диалог согласия, три PNG из MediaProjection, исключение повторного вызова и состояние сервиса. Закрашивание защищённого кадра выполняет Android, не скрипт.

**Ограничение.** Проверяется повторный `createVirtualDisplay` на одном объекте при targetSdk 34; это не перебор всех вариантов повторного использования consent Intent. Защита не распространяется на внешнюю камеру. Системные элементы могут оставаться видимыми в защищённом кадре.

**Вручную.** В Security Lab откройте опыт, в Helper начните захват и подтвердите системный диалог. Вернитесь в Security Lab. Для сохранения каждого кадра откройте Helper → «Сохранить кадр»: Helper закроется и захватит вернувшийся экран. Переключайте защиту в Security Lab. Файлы находятся в `files/capture-*.png` Helper; список: `adb shell run-as ru.securitylab.helper ls files`.

## Локальное редактирование и ограничения

Проект редактируется в Android Studio. Для первой сборки нужны Java 17, SDK 34, Build Tools 35.0.0 и Python 3.10+ с `scripts/requirements.txt`. Сначала выполните `python scripts/prepare.py`: это создаёт только тестовые сертификаты/подписи, не Kotlin. Затем можно собирать модули. Для Windows подготовлен [scripts/local.ps1](scripts/local.ps1). Основной путь — Actions; локальная настройка для него не требуется.

Перед новой локальной серией удалите `.lab-secrets` и `results`, затем пересоберите **все** APK. Никогда не обновляйте CA между сборкой APK и сетевым опытом. Не используйте лабораторные debug APK как защищённое производственное приложение: экспортированные входы нужны для управления испытаниями, `run-as` — для получения кадров, секретные тестовые данные журналируются.

Автоматизация не использует `adb root`, `setenforce 0`, подмену Keystore, принудительное разрешение MediaProjection или имитацию FBE. UI Automation вводит одноразовый PIN в системный UI; пароль не сохраняется в отчёте. Устанавливаемый из SDK образ API 34 и emulator могут получать обновления: точные версии и fingerprint сохраняются в результатах. Жёсткого обещания побитовой идентичности разных загрузок SDK нет.

Фактически выполненные проверки поставки и оставшиеся ограничения: [docs/validation.md](docs/validation.md). Источники методики: [docs/sources.md](docs/sources.md).
